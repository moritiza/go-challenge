# ADR 001: API Choice

## Context

The Estimation Service needs an API to receive membership data and provide estimates.

For the simple implementation, we want something easy to build, test, and understand.

The production-ready design uses Kafka for asynchronous event ingestion, so the API is mainly used for client queries.

## Decision

Use REST API for the simple implementation.

The simple version exposes:

- `POST /v1/memberships` to receive membership data.
- `GET /v1/segments/{segment}/estimate` to return the active user count.

In the production-ready architecture, membership events are sent through Kafka instead of the REST ingestion endpoint.

The Estimate API remains a REST API because it is a simple request/response operation.

## Why REST?

- Simple to implement and test.
- Easy to understand and use.
- Good fit for the simple assignment.
- No need for extra infrastructure for the simple version.

## Alternatives

### gRPC

gRPC could provide better performance and strong contracts, but it adds more complexity for this use case.

### Direct Kafka Ingestion

Kafka is a better choice for the production-ready design because it provides buffering, retries, and horizontal scaling.

It is not used in the simple implementation to keep the solution small and focused.

## Consequences

The simple version is easy to run and test, but synchronous ingestion has less buffering and scaling capability.

The production-ready version moves ingestion to Kafka while keeping REST for the read path.
